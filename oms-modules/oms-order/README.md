# oms-order

独立订单管理微服务，端口 9305，网关前缀 `/order`，本地数据库 `qm_oms_saas_order`。

一期支持天猫普通已付款待发货订单：从只读推送库定时拉单、按店铺和推送更新时间补拉、平台订单/业务订单/转单异常三个列表，以及需求登记和公司渠道逻辑预占。现支持店铺分仓规则和手动分仓、仓库占用、发货单生成与追溯、整单作废释放；已实现真实 WMS 下发及受理查询；出库回传、平台库存同步和已登记需求后的订单更新仍待后续接入。

## 业务状态展示与筛选

业务订单接口返回 `business_status` 作为列表、详情和业务阶段筛选的统一口径：未审核订单为 `WAIT_REVIEW`（待审核），审核通过后为 `WAIT_ALLOCATION`（待分仓）；作废处理中和已作废优先保留 `VOIDING`、`VOIDED`。分仓回执为部分时返回 `PART_ALLOCATED`；全部完成但发货单尚未齐备或有未匹配快递时返回 `WAIT_CARRIER`，全部匹配后返回 `WAIT_DISPATCH`（待下发仓库）。`documentStatus` 还支持部分发货、已发货，共十二种值，其中待分仓仅查询已审核且未分仓订单。

`status` 保留现有履约生命周期语义，审核、逻辑库存预占和人工挂起分别由独立字段维护。库存充足不自动改变人工审核结果，库存不足也不撤销已通过的审核。`release_eligible` 和 `release_blocks` 描述分仓前置条件，已审核但缺货的订单仍为待分仓，并显示库存阻塞原因；前置条件满足不代表已经分仓或已下发仓库。

后续履约按“审核通过 → 分仓及仓级占用 → 最终匹配快递 → 下发 WMS → 发货回传”扩展。指定快递作为分仓约束，物流匹配与面单取号分开管理；多仓订单按履约单管理仓库与快递。接入实际履约服务时，逻辑预占应转换或关联仓级占用，不能重复扣占。已实现分仓、仓级占用和快递匹配，WMS 下发已接入，实际出库回传尚未接入；不会将分仓完成显示为已发货。

## 逻辑预占与仓库库存

业务订单列表、详情及重试结果分别返回 `logical_inventory_status`（与现有 `inventory_status` 同值）和 `warehouse_inventory_status`。逻辑状态使用 `WAIT_RESERVE`、`PART_RESERVED`、`RESERVED`、`RELEASED`，页面明确显示待逻辑预占、部分逻辑预占、逻辑预占完成、逻辑预占已释放。列表进度为已逻辑预占件数 / 需求件数，并展示 SKU 数及剩余待逻辑预占件数；剩余件数不等同于仓库实际缺货数量。

仓库状态来自库存服务的 `oms_order_warehouse_allocation` 回执。未分仓为 `NOT_OCCUPIED`；部分/全部分仓为 `PART_OCCUPIED` / `OCCUPIED`；作废完成且有历史仓库占用时为 `RELEASED`。远程结果不确定时返回 `UNKNOWN`，重试会按来源和批次核对已有回执，不重复扣占。仓库进度字段为 `warehouse_required_quantity`、`warehouse_occupied_quantity`、`warehouse_outbound_quantity`；未接入出库时出库量为零。

## 店铺分仓规则与执行

“订单设置 → 分仓规则”独立维护货主、允许虚拟仓及默认顺序，省份优先仓仅能来自允许仓。虚拟仓经 `owner_warehouse` 映射货主和实体仓；只使用全链路启用的仓库。每单只用同一货主，多仓及同 SKU 跨仓均按虚拟仓判断。默认关闭分仓、多仓、部分发货和同 SKU 跨仓，必须明确配置后才能执行。

优先尝试整单单仓履约，省份优先仓和默认顺序作为候选顺序；无法整单单仓时，允许多仓才尝试多仓组合。关闭部分发货时整单计划不完整即全部回滚；开启时可先占用已逻辑预占且允许仓有库存的部分，余量留在原单补货重试。关闭同 SKU 跨仓时，该 SKU 的后续余量继续从首次虚拟仓分仓。相同 SKU 的平台行合并选仓，原销售数量和金额不拆改。

渠道 `LOCK` 来源绑定原虚拟仓和原规则批次，分仓继承已有物理锁库；原仓不在允许仓中视为配置冲突，不能悄悄换仓。`PUBLIC_EXTRA` 来源从允许仓选可用批次，将 WMS 可用转占用；逻辑预占汇总不二次扣减，可售计算扣除尚未转仓级占用的公共逻辑预占。分仓前核对每行预占来源合计、批次和仓库库存一致性，历史来源缺失会阻止执行，不能猜测补建来源。

接口 `POST /orders/business/allocate-batch` 接受 `items:[{id,control_version}]`，每批最多 20 单，权限 `order:order:allocate`。订单需已审核、未挂起、无平台阻断、关联一致。先持久化分仓意图，再在店铺租约/平台单/业务单锁保护下调用库存；库存事务共用公司/SKU互斥锁，回执按逻辑来源累计去重。存在分仓回执后沿用首次规则；首次失败且无回执时重试可以使用最新规则。库存服务先提交但响应丢失时，订单重试确认原回执。整单作废与分仓共享库存锁，并在同一库存事务释放公共仓库占用、返还逻辑库存；渠道锁库占用先归还原锁库余额。分仓明细可查看实体仓、虚拟仓、批次、子单、数量和来源。

执行 `docker/local/configure_order_warehouse.py` 安装本地新增表、字段和分仓权限；重建 order、inventory、supplychain 和前端。安装仅新增结构和权限，不修复业务数据、不自动启用店铺规则。

Quartz `orderPullTask.scanAll()` 调用受内部鉴权保护的扫描入口。订单服务按公司、店铺取得数据库租约，每次读取一个有界页面再处理一批订单；同店铺串行、跨店铺最多两路执行。补拉独立分页，自动任务优先，不修改自动游标。原单落库和游标推进同事务；远程库存操作使用平台订单行稳定身份去重，订单服务失败后重试关联原结果。

`oms_order_stock_demand` 由库存服务维护。拉单解析匹配后登记需求，转单更新同一条需求的逻辑预占。渠道 `available_stock` 为最终可售投影，登记需求先保护可售，待占转预占不重复扣减。普通额度基数单独保留在 `quota_stock`；每次重算按渠道总预占减去有效锁库来源占用，重建 `quota_reserved_stock`，公共逻辑预占扣减普通额度余额。取消订单自动返还额度，重新分货保留已有公共预占，即使预占早于额度分配也参与扣减。渠道锁库订单占用从 `allocated_stock` 转入 `reserved_stock`，不重复扣减普通额度。公共预占在公司/SKU层面保护剩余正品库存，此阶段不确定发货仓，不写 `wms_inventory` 或批次锁定数量。

执行 `docker/local/configure_order.py` 安装本地配置，之后构建并重启 order、inventory、goods、channel、supplychain、job、gateway。前端提供“订单”模块。推送库连接通过 `OMS_ORDER_PUSH_113_URL`、`OMS_ORDER_PUSH_113_USERNAME`、`OMS_ORDER_PUSH_113_PASSWORD` 注入；不在前端、任务日志或代码中保存密码。源表为 `sys_info.jdp_tb_trade`，按 `seller_nick,jdp_modified,tid` 增量读取，源库绝不写入。

支持两个独立推送来源：`sysinfo113` 对应 `172.16.9.113:3306/sys_info`，`sysinfo100` 对应 `172.16.9.100:3306/sys_info`。100 来源使用 `OMS_ORDER_PUSH_100_URL`、`OMS_ORDER_PUSH_100_USERNAME`、`OMS_ORDER_PUSH_100_PASSWORD`。每个店铺选择一个来源，连接池和拉取游标按来源及店铺隔离；新增来源不会切换现有店铺。配置凭据后重建订单服务容器使环境变量生效。

拉单管理中的店铺接入默认暂停自动拉单。配置真实卖家及首次拉取起点后启用；货主和允许仓在独立分仓规则中维护。补拉范围为开始时间包含、结束时间不包含的推送更新时间；不是历史订单快照。平台SKU商品编码匹配失败时保留原单，人工修正商品资料后重试。已登记需求后的原报文业务变化会标记待处理，不自动变更业务订单或释放库存。

订单设置独立提供转单设置、分仓规则、快递资料及快递规则四个页签。转单设置维护自动转单、交易类型、审单方式及公共库存逻辑补占，保存仅更新业务策略与版本；不修改拉单来源、开关、间隔、游标或错误记录。配置与接入编辑共享版本校验，防止覆盖并发修改。订单列表和异常中的配置入口定位到对应店铺与页签。

## 发货单

“订单管理 → 发货单”查看按虚拟仓生成的履约单据。分仓回执确认后，在同一个本地事务中同步分仓镜像并生成发货单；不再次预占或扣减库存。每条库存占用回执只归属一个发货单，以公司和回执 ID 唯一约束防止重复。同一次新增回执按货主、实体仓与虚拟仓归集；不同虚拟仓即使属于同一实体仓也分别生成发货单、销售出库单并下发 WMS。同一虚拟仓的不同批次保留为来源明细。部分分仓只为已占用数量生成单据，补仓只对新增回执创建新批次，不修改旧发货单。校验平台子单、SKU、原单数量、公司店铺、来源、累计回执完整性及已生成记录不可变，异常时整体回滚。

新发货单状态为 `WAIT_CARRIER`（待匹配快递），已发货数量为 0。订单列表及明细区分已分仓、已发货、待分仓数量。订单明细支持按已确认回执补建历史发货单，使用订单版本、店铺租约和订单行锁校验；不在读取或安装时自动补建。

整单作废申请将未下发发货单同步冻结为 `VOIDING`，库存服务确认需求与占用释放后才变为 `VOIDED`，保留历史单据数量和来源。已有仓库处理、下发中或出库数量的单据禁止直接整单作废。当前未提供独立发货单作废或出库数量手工编辑；后续接入真实仓库回传后再推进发货状态与数量。

## 发货单快递匹配

订单设置中的快递资料维护公司快递编码、名称、启用状态及货主实体仓服务范围，服务配置包含仓库快递编码、配送省份与排除省份；不内置或自动启用未经配置的真实快递。省份按行政名称归一化，必须有可识别的来源订单省份，不从拼接地址猜测。店铺规则维护允许快递和默认顺序，以及实体仓/省份的优先顺序。采用仓库与省份、仓库默认、全仓省份、店铺默认的优先级，再按店铺默认顺序补充候选。所有候选均须启用且支持该货主实体仓和区域。

新发货单在建单事务中自动尝试匹配；配置缺失、自动关闭或无可用快递时保留 `WAIT_CARRIER` 并记录失败原因，不影响分仓占用和单据数量。成功后进入 `WAIT_DISPATCH`，保存快递名称、仓库编码、匹配人/时间、规则及服务范围快照。部分分仓与补仓的新发货单独立匹配，已有快递不因规则修改或自动重试而覆盖。

发货单列表支持最多20张批量自动匹配，详情支持自动重试及手工调整。手工调整要求填写原因，仍校验店铺允许快递、仓库和区域。每单事务与作废/分仓共用店铺、平台单及订单锁，再锁发货单并校验版本；人工挂起、平台阻断、未审核、来源已停止履约、仓库停用、已下发/处理中/作废或已有出库数量均不能调整。匹配不调用库存写入接口。权限 `order:shipment:carrier` 独立控制匹配操作，配置仍使用 `order:pull:config`。

安装 `docker/local/configure_order_carriers.py` 后重建 order 与前端；安装只新增结构和权限，不选择真实快递、不改已有业务单据。接口 `GET /orders/carrier-catalog`、`POST /orders/carriers`、`GET/POST /orders/carrier-configs` 管理配置；`GET /orders/shipments/{id}/carrier-options` 提供可选项及不可用原因；`POST /orders/shipments/match-carrier` 接收 `mode:AUTO/MANUAL, items:[{id,control_version}]`，手工模式另外传 `carrier_code,reason`。发货单详情展示匹配日志。匹配成功仅代表路由已确认，不代表已下发、已取面单或已发货。

业务订单详情的发货单页签提供单张自动匹配、手工选择或调整，以及匹配全部可操作的待匹配发货单。超过20张时前端按20张顺序分批提交，逐张展示成功、失败或未确认结果；网络失败停止后续批次并刷新当前状态，不能将未知结果当成确定失败自动重发。跳过已匹配、挂起、阻断、已下发或已有出库数量的单据；操作完成后刷新订单详情、关联发货单和订单列表。

## 发货单下发 WMS

复用采购入库的 `wms_connection`、加密凭证、虚仓对接映射和 `wms_interaction_log`，新增发货单下发任务，不复用采购入库单表。出库适配按[奇门发货单创建](https://developer.alibaba.com/docs/api.htm?apiId=26002)、[奇门发货单查询](https://developer.alibaba.com/docs/api.htm?apiId=24690)及[京东虎符 ERP-WMS 2.4 文档](https://hufu-doc.s3.cn-north-1.jdcloud-oss.com/%E4%BA%91%E7%89%A9%E6%B5%81%E8%99%8E%E7%AC%A6erp-wms%E6%8E%A5%E5%8F%A3%E6%96%87%E6%A1%A3_v2.4.pdf)实现，支持 QIMEN 2.0 和 JD_HUFU 2.0；已有虎符1.0采购入库能力保留。统一使用一般交易出库 `JYCK`、发货单号作为稳定外部标识，逐行携带平台子单、SKU、数量和真实库存批次编码。匹配到的仓库快递编码用于下发。

发货单列表、详情和业务订单详情发货单页签均提供下发、明确失败后的重试及查询入口。下发前预览连接、协议、测试/正式环境、外部仓库和货主，按单返回校验原因。虚仓必须明确配置 `outbound_mode=1` 并绑定可用连接；自动虚拟出库不调用真实 WMS。同一发货单所含虚仓必须属于同一货主实体仓并映射同一个连接、外部仓库和货主，不能任意选择某个虚仓的连接。补仓的新发货单独立下发，不能改动已下发快照。

订单端先在店铺、平台单、业务单、发货单锁及版本保护下提交持久化意图，再由独立后台任务发送。后台发送前重新检查审核、挂起和平台阻断，并在同一锁范围内执行有超时限制的仓库调用。供应链端保存相同单号和内容摘要的任务、条件抢占发送租约；重复提交返回原任务，相同单号不同内容拒绝。连接被出入库任务使用后其目标身份不能变更，凭证仍可轮换。任务和请求日志不改库存余额、占用或实际已发货数量。

结果字段 `wms_dispatch_state` 为 `NONE/PENDING/PROCESSING/ACCEPTED/FAILED/UNKNOWN/CANCELED`。提交后发货单进入 `DISPATCHING`，收到仓库明确接收及外部单号后进入 `WAREHOUSE_PROCESSING`；明确失败回到 `WAIT_DISPATCH` 并允许按原快照重试。超时、响应损坏、可能重复或进程中断保持待确认并查询，查无单据或任务记录缺失不能成为重新创建的依据。查询 `DELIVERED`、部分发货或关闭状态只记录仓库状态，等待完整出库明细回传，不直接增加已发货数量。已知受理结果与本次查询是否成功分别保留。

业务订单全部分仓后依次派生待匹配快递、待下发、下发处理中、部分下发或仓库处理中；部分分仓仍显示部分分仓并展示各发货单状态。下发意图建立后快递快照冻结。提交中、待确认及已受理单据不能本地直接整单作废；只有明确失败且无外部单号的任务可以随本地作废停止。真实仓库取消、出库确认和库存扣减属于后续独立流程。

安装 `docker/local/configure_order_dispatch.py` 后重建 order、supplychain、inventory 与前端。只新增结构和权限，保留所有连接、虚仓执行方式、快递规则及业务数据，不提交现有发货单。权限 `order:shipment:dispatch` 控制预览/下发，`order:shipment:queryWarehouse` 控制查询；交互日志复用 `warehouse:wms:log/payload`。接口 `POST /orders/shipments/dispatch-preview`、`POST /orders/shipments/dispatch` 接收 `items:[{id,control_version}]`（每批最多20张），`POST /orders/shipments/{id}/query-warehouse` 查询已有任务。业务订单详情的“全部下发”按20张顺序分批提交，仅提交预览通过项，网络不确定时停止后续批次。


## 虚拟出库

仓库 `outbound_mode=2` 时，无需 WMS 连接、外部仓库或货主编码。发货单列表、发货单详情及业务订单详情提供虚拟出库入口，支持单张输入各来源行的本次数量和批量全部剩余数量出库。全部来源虚仓必须启用、货主及实体仓一致，并统一使用虚拟模式；混合模式先核对仓库配置。快递匹配、审核、挂起、平台阻断及版本校验仍生效。只在原分仓规则快照允许部分发货时接受部分数量；不会因安装或读取而自动出库。

订单服务先持久化固定出库指令并冻结单据，任务定时核对库存回执后处理。库存服务以公司及请求号去重，在同一事务扣减对应批次和仓库正品实物、占用数量，以及公司总库存、公司和渠道预占余额。可用库存不因出库增加。渠道锁库来源从占用转已消耗；公共库存同步核销已使用的普通额度，不将已售额度返还可售。原需求、预占和分仓数量作为累计历史保留，`outbound_quantity` 记录核销数量，所有可售保护计算只使用剩余占用。库存流水、出库回执和全部库存变更同事务提交；任一来源或余额异常整体回滚。

订单仅在库存回执身份、数量和逐行来源全部核对通过后更新 `shipped_quantity`，显示部分出库/已出库，业务订单显示部分发货/已发货，仓库库存显示部分出库/已出库及剩余占用，逻辑预占显示部分核销/已核销。核对失败会回滚整次本地进度更新。响应丢失只核对原请求：已经记账的回执可以在挂起后同步；尚未记账时仍受挂起、平台和仓库配置门禁保护。明确失败可按原快照重试，不重新选择数量；已有虚拟任务禁止调整快递、切换为 WMS 下发或直接整单作废。

权限 `order:shipment:virtualOutbound`。接口：`POST /orders/shipments/virtual-outbound-preview`、`POST /orders/shipments/virtual-outbound`，均接受 `items:[{id,control_version,lines?:[{id,quantity}]}]`（每批最多20张；省略 lines 时处理全部剩余量）；`POST /orders/shipments/{id}/retry-virtual-outbound` 按当前版本重试原失败任务；`POST /orders/shipments/{id}/query-virtual-outbound` 只核对回执。出库请求按公司、发货单及提交前版本固定，重复提交相同参数返回原任务，变更参数被拒绝。

执行 `docker/local/configure_order_virtual_outbound.py` 只新增结构和权限，随后构建 order、inventory、supplychain 及前端；不修改仓库模式，不出库既有订单。虚拟出库不生成 WMS 受理记录，也不伪造运单号；平台发货回传和真实 WMS 出库回传另行接入。


## 出库回传、出库记录和运单

真实仓库出库沿用 `/wmsCallback/{company}/{callbackKey}` 及现有连接凭证、租户路由、MD5原文签名和交互日志。奇门支持标准 ERP 方法 `deliveryorder.confirm` 及完整方法名，虎符2.0使用JSON适配。实现依据：[奇门发货确认接口](https://developer.alibaba.com/docs/api.htm?apiId=26001)、[ERP回传规范](https://developer.alibaba.com/docs/doc.htm?articleId=118403&docType=1&treeId=813)。回传须包含唯一消息ID、仓库、发货单、商品数量和包裹；按原下发快照、行号/SKU/批次、货主及外部仓库单号核对。头部货主可以从一致的明细货主取得，已受理单据可沿用已绑定的外部单号。正品数量必须为整数（允许 `1.0` 形式）；不自动处理未知库存类型、无法唯一映射的来源或未实际下发单据。

仓库对接侧在本地事务保存回传事件及包裹明细，不直接改订单库存。相同消息ID只能重复相同内容；相同包裹即使用新消息ID重传，也不重复出库。累计包裹报文会剔除已确认包裹，只有新增包裹形成库存记账增量；包裹运单或数量变化、行与包裹数量不符、累计超出原单都会拒绝。最终确认不会将未出库余量伪报为已发货，也不会自动释放余量。

订单服务以回传事件固定库存请求，先核对原回执再使用与虚拟出库相同的原批次、来源核销事务；两种出库方式有独立标记，不能混用。订单发货进度、包裹、运单和出库记录在同一本地事务确认；库存响应丢失只核对原请求，本地核对失败会整体回滚进度与包裹，仓库记账结果确认丢失只补确认。前次记账未完成时不为后续回传建立过期的数量快照。已发生的、验签通过的真实出库允许在订单挂起后记账，挂起不能抹除实物出库事实。

虚拟出库确认后可人工登记一个或多个包裹；只能选择已出库且尚未登记运单的行数量，不再次消耗库存，不生成虚假运单。运单默认在公司与快递范围内唯一；同一业务订单的WMS包裹经人工核对确认后可共用运单，包裹编码、来源明细和实际数量仍独立保留。重复请求/重复包裹按原内容核对；WMS运单以仓库回传为准，不能人工替代。详情展示每次出库数量、来源、时间、记账结果，以及包裹快递、运单、平台子单和商品数量。查询仓库受理状态不会把部分出库或已出库退回仓库处理中。

权限 `order:shipment:package`、`order:shipment:receipt`。`POST /orders/shipments/{id}/packages` 登记虚拟出库运单（版本、稳定请求号、运单号、可选包裹编码/时间、逐行数量）；`POST /orders/shipments/{id}/reconcile-receipts` 核对并重试本发货单原回传。详情只读返回 `outbound_records`、`packages`、`packaged_quantity`、`unpacked_quantity`。仓库回传与人工登记只记录实际出库和包裹。平台通知由独立回传任务处理，当前仅开放本地模拟，未调用真实平台接口。

执行 `docker/local/configure_order_receipts.py` 安装结构、权限及已有虚拟出库的历史展示镜像，不修改实物库存、不自动下发。`docker/local/seed_outbound_acceptance.py` 是用户明确要求保留的单据验收入口：创建独立测试店铺及SKU，暂停拉单和自动转单，模拟销售需求，经实际库存、分仓、虚拟出库、运单登记接口形成8件订单、两次出库共6件、两个测试运单，保留2件余量；不连接推送源，不向平台或真实仓库发货。结果保存 `outputs/outbound-acceptance/retained-test.json`，脚本不会删除验收数据。

## 发货单下发确认与结果

下发预览返回本次发货单的商品、规格、平台子单、虚仓、库存批次及数量。单张默认展开，批量按实体仓和货主分组；混选时只提交校验通过的发货单，未提交单据保留原因。商品汇总仅用于展示，实际下发仍保留来源明细行。明确失败重试的预览及详情使用已持久化的原下发快照，不重新生成商品、快递或批次数量。

提交结果每3秒只读刷新本地下发状态，最多40次，关闭弹窗停止刷新。结果待确认时仅提供仓库核对，明确失败才允许重新校验并重试；仓库已接收与实际出库进度分别展示。列表支持 `dispatchState` 筛选及首次提交、最近处理时间。`docker/local/verify_shipment_dispatch_ui.py` 拦截全部订单业务请求进行浏览器验收，不向真实仓库下发。

## 仓库交互日志与本地模拟

仓库交互日志支持动作及结果筛选，单据摘要独立展示首次、最近下发记录，历史创建记录不会被后续查询分页遮蔽。`GET /wmsIntegration/log-summary?sn=...` 只返回日志元数据；报文仍受独立权限及脱敏保护。

本地环境的 `wms-simulator` 使用持久化 SQLite 模拟奇门2.0创建、查询及取消，校验签名和请求时间，按客户、货主、仓库及单号去重；返回带 `SIMOUT_` / `SIMIN_` 标记的受理结果，不自动产生出入库回传或通知销售平台。通过 `docker/local/configure_local_qimen_simulator.py` 创建独立 TEST 配置，凭证文件已忽略入库。已使用的原连接保持不变。`repair_yapi_test_dispatch.py` 仅用于已明确授权的指定 YApi 误路由测试单，停订单任务后原子迁移目标与双方快照，保留原日志及恢复审计；不能用于正式连接或已有出库单据。

用户明确授权后，执行 `python docker/local/simulate_qimen_delivery.py <XS发货单号>` 可模拟该本地 TEST 发货单的全部商品实际出库，使用原下发 SKU、行号及批次签名回传，正常扣减本地业务库存，生成一个 `TEST-` 运单。稳定消息和包裹身份保存在 `outputs/warehouse-shipping`，重复执行不重复扣账。仅允许绑定本地模拟地址的已受理单据，不支持正式仓库或无原事件的部分出库单；服务自身不自动触发发货。

## 销售出库单据台账

新生成的订单发货单使用 XS 前缀。统一出入库台账仅为新建 XS 来源发货单、虚仓生成稳定的 XS 销售出库单，不补录历史单据。记录来源业务订单、渠道及平台单号。计划明细按原发货行与库存批次保存，逐次实际出库只复制已确认并已扣库存的出库回执；同步不会再次扣库存或下发 WMS。

`oms_order_sales_document_sync` 保存同步快照、递增版本与确认结果，后台重试未确认的数据。供货链按公司、发货单和虚仓幂等落入 `wms_tickets` / `wms_tickets_goods`，逐次明细保存在 `wms_sales_outbound_movement`；较早同步版本不会覆盖较新的同步版本。统一台账支持业务类型、出入库方向、单据与商品明细视图。销售出库的执行与取消继续从来源订单发货单操作，采购入库接口拒绝销售出库单。部署先执行 `docker/local/configure_sales_outbound_documents.py`，再更新订单与供货链服务。

## 补拉订单

`TIME` 补拉不限制固定90天，结束时间晚于服务器当前时间时自动截断，仍要求开始早于实际结束。任务每次只读取一个24小时窗口的一页，空窗口继续推进，整体完成才结束；补拉不修改自动拉单游标。任务按待执行时间公平调度，避免大范围补拉或自动拉单长期占用队列。

`TID` 补拉每次一个店铺、1至100个文本单号，按卖家和 TID 精准读取配置的只读推送库，不附加时间范围，也不会自动查询其他店铺或平台接口。任务固定创建时的来源绑定，绑定变化后拒绝继续读取。`oms_order_pull_item` 保存逐单查询和平台同步结果，转单状态按平台订单实时展示。单条保存失败通过保存点回滚，不影响同批其他订单；失败项重试创建新的 TID 任务，不重拉成功项或未找到项。提交请求标识保护网络重试的幂等性。部署先运行 `docker/local/configure_order_backfill.py`，再更新订单服务。

仓库核对结果同时显示受理与实际出库进度。`wms_fulfillment_state` 和 `wms_progress_message` 按已处理回传的出库数量、包裹及待核对记录实时生成；刷新或再次查询不能用旧的等待回传提示覆盖已出库进度。仅仓库查询返回 `DELIVERED` 而没有实际出库回传时仍显示等待回传，不据此扣库存。商品保留原下发快照，并按来源行 ID 叠加当前实际出库及剩余数量。

包裹展示按业务订单 → 虚拟仓（标明实体仓/货主） → 发货单 → 实际包裹组织。分仓明细提供每仓出库、余量、实际包裹计数及只读查看入口；包裹刷新发现数量变化时同步刷新父级汇总。包裹卡片展示运单、来源、出库时间和按 SKU 汇总的实际商品数量，来源行保留平台子单、虚仓及批次。未出库、已出库未关联包裹与读取失败分别展示，不推算包裹数量或展示尚未接入的揽收/签收状态。仅显式本地模拟工具生成的 `SIMPKG_` 包裹配合 `TEST-` 运单标记为模拟运单。


统一问题标签首批接入库存域：`SHORTAGE` 库存不足、`QUOTA` 额度不足、`RESTRICTED` 库存受限、`LEDGER` 台账异常。原因码、层级（公司/渠道/仓库/批次）、阶段、提醒/阻断、SKU和证据分别记录，可扩展其他业务域。`oms_order_issue` 保存当前及已解除问题，`oms_order_issue_event` 保存发生、变化、确认、解除与再次发生的依据；确认只表示知悉，不解除阻断，不修改任何库存数量。

库存服务提供只读批量核对接口，按公司、渠道、平台单号校验需求和来源；订单服务每30秒分批同步活跃订单，并允许单单刷新核对。列表按问题类型、层级、影响与状态筛选；商品明细显示渠道锁库/公共补占来源。已解除问题移入记录；核对失败或返回身份/明细不完整时保留原问题，不能按空结果清除。公共补占属于来源说明，不是缺货标签。正常预占使公司可用变为0时，只要需求已满足就不会标记公司库存不足。

新预占尝试在 `oms_order_stock_demand.decision_snapshot` 记录当时余额、渠道额度与补占需求。既有记录不补造历史快照；当前订单按实时余额和自身来源核对，排除自身已预占数量对渠道额度的重复扣减。问题详情明确区分当前核对与预占尝试快照。结构安装：`docker/local/configure_order_issues.py`，没有库存回填或预占策略变更。


## 平台发货回传（模拟验收阶段）

从发货单列表、业务订单发货单和发货单详情进入“平台发货回传”。店铺配置在发货单页面，默认关闭，只允许 OFF / SIMULATION；真实接口尚未启用，当前模块没有 TOP 发货调用。模拟模式仅接受 TEST- 运单，开启后自动扫描新增测试包裹，既有测试单据须显式生成任务，不补录历史订单。

`oms_order_platform_shipping_config` 保存店铺开关及 OMS→平台快递编码映射。`oms_order_platform_shipping_task` 按公司、包裹唯一，冻结 TID 文本、OID→本包裹数量、来源明细、快递、运单与商品校验摘要。多个仓库及同一子单分数量发货均按包裹增量处理；单个包裹成功不能把剩余未出库商品标为已发货。生成前核对出库入账、累计数量及子单来源，回传绝不改变仓库状态、包裹数量或库存。

任务状态 PENDING / PROCESSING / SUCCESS / FAILED / UNKNOWN 与仓库状态独立，页面明确标记模拟成功。确定的临时失败最多自动重试3次，人工重试继续使用同一请求和快照，累计提交次数保留。发送结果不确定或处理租约超时后只查询原回执，即使关闭店铺也允许核对，不按“查询不到”直接重新发送。并发领取通过带租约的条件更新防重，回复丢失通过独立持久模拟回执恢复。

`oms_order_platform_shipping_log` 保留生成、发送、核对和人工重试记录。模拟平台回执在 `oms_order_platform_shipping_sim_receipt`，显式 SIMSHIP_ 前缀，不能视为天猫真实发货成功。失败或待确认接入通用 PLATFORM / PLATFORM_SHIP 问题域，重试中保留问题，确认成功后解除，不能被库存核对任务清除。

部署先运行 `docker/local/configure_platform_shipping.py`，再更新订单服务和前端。验收脚本 `verify_platform_shipping_flow.py --enroll-retained` 仅将保留的 XS870a08cfdade45b5be4ad60d3cc802ab 测试单据加入模拟回传，`verify_platform_shipping_ui.py` 只读真实数据并拦截失败/待确认按钮场景。正式回传需后续接入店铺接口授权、真实快递映射及平台按数量部分发货能力核验。

分仓的允许多仓、同 SKU 跨仓和补分仓固定仓均以虚拟仓为单位。优先尝试一个虚拟仓满足整单，再根据开关组合允许虚拟仓。关闭同 SKU 跨仓时，其已分配或继承渠道锁库的虚拟仓保持固定；不会因为属于同一实体仓而跨虚拟仓取货。分仓不创建包裹，包裹以实际出库回传或虚拟出库后的登记为准。本次规则变更不重分配、不拆改历史单据。

## 被拒绝的仓库回传人工核对

签名和绑定身份验证通过的运单冲突进入 `wms_outbound_receipt_review` 待核对队列；接收失败仍返回失败应答，本次不生成库存出库指令。保留归一化原回传、校验摘要、消息号和原交互日志ID，不从历史失败日志补录。无效签名、错误仓库/货主及数量或批次异常不能通过共用运单审批绕过原校验。

发货单详情的“仓库回传核对”对照本次包裹、原关联发货单和商品数量，显示本次未扣账、已扣账或扣账结果待确认。权限 `order:shipment:receiptReview` 控制人工处理。填写原因并勾选核实声明后，可“确认共用运单并补记出库”，或“拒绝本次回传”。共用仅限同一业务订单，已接收包裹的运单或数量变化不能直接覆盖。处理人、结论、原因、时间和原出库事件保留；重复确认沿用第一次处理结论。

确认在仓库侧事务中重新验证原快照、批次、数量上限、原包裹完整性并生成唯一待记账事件，随后由正常回传处理链路提交固定库存请求。库存成功后才更新发货进度与包裹。确认响应丢失可刷新查看结论，后台仍按原事件继续处理；扣账响应丢失先查询原库存回执，不重复扣减。人工拒绝不发布库存指令。经过核对的包裹显示“已核对共用运单”。当前平台发货仍为独立模拟任务，不向真实平台发送。

部署前运行 `docker/local/configure_receipt_review.py` 安装队列、运单互斥行和明确审批后的运单身份槽，保留原包裹唯一性及所有库存数据；再重建 order、supplychain 与前端。`GET /orders/shipments/{id}/receipt-reviews` 查询当前公司的发货单，`POST /orders/shipments/{id}/receipt-reviews/{review}` 接受 `decision:CONFIRM_SHARED/REJECT`、`control_version` 和必填 `reason`。公司、操作人、关联同订单发货单范围由服务端决定。

## 中央定时调度

仓库下发、出库回传记账、虚拟出库、销售出库单同步、平台发货回传、库存问题核对与采购入库仓库交互，统一由 ruoyi-job 的 `fulfillmentScanTask` 七个固定方法触发。order 和 supplychain 不再启用上述服务内部 `@Scheduled`。系统“定时任务”选择“订单与仓库扫描”可集中查看，沿用原有启停、cron 修改、立即执行和日志权限。停止只影响后续扫描，业务单据处理仍使用原租约、事务和幂等请求。

全公司扫描仅允许精确白名单路径的内部认证 POST，请求进入后由扫描器遍历明确配置的数据源和公司；退出及异常时清理线程路由。其他路径、无内部认证的请求不能获得全公司扫描能力。收货扫描按 WMS 的公司路由执行，不使用数据源组随机选库。

日志保存在 `sys_job_log.execution_data`，只包含本轮计数和最多50条脱敏单据引用，不保存原始报文、接收人信息或连接密钥。扫描范围异常、业务失败、结果待确认与待人工核对存量分别统计。待人工核对记录仅展示、不审批、不创建扣账事件；执行明细可进入原单继续人工核对。旧 void 类型定时任务日志保持兼容。

部署时先执行 `backup_fulfillment_jobs.py` 备份配置和日志，再执行 `configure_fulfillment_jobs.py` 安装日志字段及七个暂停的新任务。该脚本重复执行不会覆盖已有开关或cron。更新 order、supplychain、job 和前端并确认内部自动触发已移除后，逐项立即执行验证，再启用新任务；避免新旧调度同时运行。本地验证为 `test_fulfillment_jobs.py`、`test_orders.py --order-only`、`test_purchase_workspace.py`。`activate_fulfillment_jobs.py` 使用真实 Quartz 验证暂停、立即执行、恢复和自动触发，并核对原验收单的核对结论与库存相对切换前快照未改变；`verify_fulfillment_jobs_ui.py` 为只读页面验收。证据在 `outputs/central-scheduler`。
