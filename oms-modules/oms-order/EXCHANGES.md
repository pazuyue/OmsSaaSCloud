# 换货申请与订单更新

入口为“订单管理 → 换货管理”；店铺开关在“订单设置 → 换货接入”。平台申请自动同步为处理单，自动创建不等于人工审核、同意平台申请或修改库存。新定时任务“天猫换货申请同步与履约扫描”由 ruoyi-job 统一触发；沿用有界后台执行器与数据库待办，不新增 MQ。

## 平台接口

渠道服务使用现有店铺绑定、授权、TOP 签名和交互日志，仅允许以下操作：

| 业务 | 官方接口 |
| --- | --- |
| 同步列表 | `tmall.exchange.receive.get` |
| 完整详情及原操作核对 | `tmall.exchange.get` |
| 同意申请 | `tmall.exchange.agree` |
| 拒绝原因 | `tmall.exchange.refusereason.get` |
| 拒绝申请 | `tmall.exchange.refuse` |
| 确认退回收货 | `tmall.exchange.returngoods.agree` |
| 换出发货 | `tmall.exchange.consigngoods` |

文档：[列表](https://developer.alibaba.com/docs/api.htm?apiId=31198)、[详情](https://developer.alibaba.com/docs/api.htm?apiId=31194)。读写分别配置；本地模拟开关由可信应用配置决定，普通请求无法切到模拟。启用本地开关不代表已获得真实平台接口权限。当前真实应用权限尚未验证。

普通换货按“审核 → 检查并预占换出库存 → 同意平台申请 → 实际退回入库 → 人工验收 → 平台确认收货 → 换出履约 → 回传换出物流”执行。极速换货仅识别并阻断普通执行，转平台处理。平台售中阶段不代表原订单未发货；未知阶段保留待确认。

## 数量、库存与来源

平台申请按公司、店铺、申请 ID 幂等接入；旧版本留快照，同时间不同内容阻断。已审核数量、目标描述或收件信息变化后要求核对。按原平台子单匹配原商品，规格描述不猜测为 OMS SKU。平台数量不被人工静默缩减；可处理数量不足时保持原申请并提示协调平台。

换出库存使用独立引用 `EXCHANGE:<处理单ID>`，订单仍显示真实原平台单号。不创建新 SO 或 `EXCHANGE_PLAN` 平台单。原 SO 始终是交易入口；`oms_order_line` 新增不可变履约明细，标记 `SALE` 或 `EXCHANGE`，通过 `source_line_id`、`source_shipment_line_id` 和 `exchange_id` 保留前后关系。实际出库后的换出 XS 标记 `EXCHANGE`，出入库台账分别为 `EXCHANGE_OUT` / `EXCHANGE_IN`，归属本次 HH 换货单，同时直接关联原 SO。原交易商品、原销售出库和付款金额不覆盖。

退回走专用奇门 `returnorder.create/query/confirm`、HHRK；换出走 HHCK。只有验签并核对原退回单、连接、仓库、货主和商品数量后的实际入库事件才能增加库存。固定事件行号保证重复回传不重复入库；良品进可用，次品进冻结，人工验收不重复增库存。仓库查询成功或平台状态变化不能代替实际入库。

平台写操作先持久化原请求；响应未知后只查询原结果，不盲目重复提交。已产生库存请求的方案不能直接改写。平台申请关闭或条款变化时保留已执行事实并阻断换出新增履约。

## 客服协商换货与更新关联

客服有协商依据时可单独创建 INTERNAL 处理单；这不是伪造的平台换货申请。创建后暂停原订单新增履约，人工解除普通挂起也无法绕过换品核对。审核后先 REPLAN 撤回原未发货分仓，仓库截停确认后 REDUCE 终止所选旧商品需求，再预占新 SKU、向原 SO 追加 SALE 履约明细；原 SO 重新审核、分仓并发货。部分换品保留未更换数量，不重建整张订单。原已出库数量不回滚；其他人工挂起和阻断保留。未生效方案遇到原平台新版本时要求重审；已生效换品不因旧审核快照阻止后续合法订单更新，未解决的平台差异仍按订单更新规则阻断。

订单更新按精确差异哈希关联，审核时只是 LINKED。已确认的履约变更生效后才标为 APPLIED；当前仅自动解除可证明覆盖的 INTERNAL 全量 `outer_sku_id` 替换差异。数量、金额、退款和其他未证明覆盖的差异继续阻断，不把整条更新笼统标为已处理。

## 本期边界

- 一份普通平台申请当前须选定一条足量的实际发货明细；跨多条发货明细的退回尚未扩展，当前不猜测来源。
- 平台换出接口本期只自动提交一组承运商及运单；多运单保留人工核对，不取第一条冒充全部。
- 已有库存需求或换出单后，条款变化保留原请求并阻断，暂不提供任意改写或强制完成。
- 不包含极速换货自动执行、补差价、自动审单或历史单据补录。

## 连续换货 A → B → A

同一平台 OID 下，初购 A 的发货明细 L1、第一次换出 B 的 L2、第二次换出 A 的 L3 都有独立 ID。第二次 A 的来源指向 L2，不能复用 L1；再次换货或退款退货应选择 L3。每次申请数量以所选实际发货明细的已出库数量减去该明细已有有效申请量计算，不按 SKU 汇总恢复旧额度。审核时锁定实际来源，审核快照保存来源 XS、行 ID、SKU 和成本；库存退回沿用该来源成本，重复回传不重复入库。

原 SO 详情的销售发货数量只统计 SALE；“售后换出记录”单独列出每次 HH 与 XS。换货详情提供精确退回来源选择和“换出发货”页签；普通销售平台回传排除 EXCHANGE，由 HH 的换货发货接口回传。售后退款产品尚未实现，本期已保留其所需的交易根与实际履约来源。

未发货 A → B → A 同样追加新行：原 A 行保留取消数量、B 行被后续方案终止、最终 A 是新行。独立库存引用避免与原 A 预占台账冲突，分仓上限与同 SKU 跨仓约束仍按整个销售订单校验。

所有换货单统一使用明确的 `fulfillment_mode`：未发货替换为 `UNSHIPPED`，退回后换出为 `RETURN`，无流程版本兼容分支或只读限制。

## 售中 / 售后分类与协商退回换出（2026-10-17）

`source_kind` 只表示 PLATFORM / INTERNAL 申请来源；`source_phase` 表示 DURING_SALE / AFTER_SALE / UNKNOWN 交易阶段；`fulfillment_mode` 表示 UNSHIPPED / RETURN 实物履约。列表分别筛选阶段和来源，所有待办计数沿用同一筛选。平台不能识别的阶段保留待核对；客服创建 RETURN 时必须明确选择阶段，不根据已发货或退回方式推断售后。

客服协商现在支持已发货商品。审核锁定实际发货行、来源成本、退回仓、买家寄回地址及联系人、换出收件信息和协商依据。检查并预占换出库存后准备专用退回任务；实际退回入账、人工验收后生成归 HH 的 EXCHANGE 履约，换出全部出库并完整关联包裹后完成。原 SO 的 SALE 数量、金额和发货事实保持独立，不为协商售后挂起整张原销售订单，不调用平台换货写接口。UNSHIPPED 仍按原撤回、终止需求和原单发货流程处理。

平台和协商 RETURN 按相同 source_shipment_line_id 共同计算已审核申请占用量，审核在来源行锁内再次校验；不同代次 A→B→A 不按 SKU 合并额度。客服未发货换品不消耗已发货退回额度。

详情新增懒加载“退回与验收”页签：

- 退回要求、买家寄回物流（平台同步 / 客服登记）、仓库实收批次、良品 / 次品、记账结果、被拒回传原因和交互日志。
- 登记物流不会记账。数据暂未加载或失败显示未知，不显示为零。
- 验收支持等待补退、待仓库复核、联系买家、暂缓换出及差异核对后继续换货，记录依据、凭证引用和处理人。仓库复核是人工待办记录，不伪造仓库复核 API 指令。
- 足量实际入账且最终收货完成才能验收通过，不能以人工放行缩减应退数量。错货、超量或最终少量被拒的原回传保留在日志，不直接成为有效库存。
- 查询仓库原单、重试明确失败下发、重试原回执记账均操作原任务；结果不明不允许盲目重建。
- 明细只在打开页签时读取；扫描与订单缓存只保存退回摘要，不反复复制批次、回传和日志明细。

已审核的协商 RETURN 可核对关联同公司、同店铺、同原单、同子单及同数量的未执行平台申请，必须明确确认买家、目标及实际来源一致。原平台申请保留自己的单号和关联指向，禁止重复审核、库存和履约；平台同意、确认收货和物流操作需要在平台人工核对。后续关联平台条款变化或关闭，会阻止未结束协商单新增履约，不回滚已执行库存事实。

迁移仍使用 `configure_exchanges.py`，仅补充字段及既有权限，不回填历史业务单据。验收脚本 `verify_negotiated_exchange.py` 使用独立 TEST 商品与仓库，证据保留在 `outputs/exchange-after-sales/`：一张协商换货完成，一张保留应退 2 / 实收及入账 1、等待补退；原销售出库仍为 10。

## 退回与换出截单（2026-10-17）

- `oms_exchange.fulfillment_hold` 明确阻止新增平台写操作、库存预占、换出明细生成、分仓和下发。普通挂起不通知仓库，原有效实收实发仍按原回执处理。
- `oms_exchange_control` 保存单据截单及整张换货取消意图。操作前校验公司、原单归属、控制版本和执行租约；外部结果不明或回执待核对时保持挂起，不释放待确认占用。人工核对只继续原请求。
- 退回单 `wms_exchange_return` 按换货单和 generation 唯一。初次审核快照不覆盖，重新安排仅生成未实收的全部剩余数量，要求原安排已明确结束且无待核对回传。新单保存独立仓库、寄回地址及联系信息，保持挂起直到人工恢复。
- 退回截单接入奇门通用 `taobao.qimen.order.cancel`，类型 HHRK；换出继续使用已有取消协议，类型 HHCK。HTTP 超时或身份不一致不认定成功，只核对原单。查询状态不能代替实际收货/出库及库存记账。
- 截单确认后的退回通知存入 `wms_exchange_return_review`，重复通知不新增待办或库存。确认实收要求其他退回安排已结束、总量不超申请、原发货来源额度仍可用；按原消息和原成本幂等记账。拒绝后重复通知仍不记账。
- 待核对实收保护保留。仅对从未下发、零尝试、无仓库单号、零实收/入账且无有效回传的新安排，允许先本地撤回，便于处理旧单迟到实收；有仓库执行的新安排仍需先核对回传，不放宽仓库截单保护。
- 换出撤回在仓库明确停止及回传全部核对后，以不可变 CFHH 请求撤回物理分仓并保留逻辑预占；终止剩余释放对应未发占用。原出库数量、包裹和销售事实不回滚；重新分仓生成新发货单。
- 整张取消先暂停，再分别核对退回和换出。没有实收实发时才记 CANCELED；存在执行事实进入 CANCEL_REVIEW，填写后续处理结论和凭证后记 CLOSED，保留来源额度、入账和出库事实。OMS 结束不冒充平台申请取消或退款成功。
- 出入库台账保留计划、实际和剩余截停数量，部分执行后标识“剩余已截停”，不再提示继续收发已终止数量。所有仓库取消、查询及人工核对可从统一交互日志追溯，本地撤回明确标为 LOCAL。

验证：`docker/local/test_exchange_controls.py` 在隔离测试库覆盖控制版本、公司和单据范围、普通挂起、实收未入账、迟到通知、人工接收/拒绝、库存未知结果、原请求重试、部分出库及台账展示。`docker/local/verify_exchange_controls.py` 仅使用本地 TEST 仓库，保留原 SO、完整撤回重开和取消结果，以及待验收的两次退回安排。

## 截停后继续换出

已结束或剩余换出需求已终止的退回换货，可在原 HH 申请“继续换出”。原退回必须全部入账且验收通过，原需求及截单已确认终止，所有退回/换出回传均无待记账或待人工核对。数量固定为批准总量减各轮实际已发总量，目标 SKU 沿用原审核；重新确认本轮地址、买家协商依据及无退款/冲突售后，再由审核人独立审核。

申请和拒绝不会创建库存需求；批准后新轮次使用独立 `EXCHANGE:<id>:<round>` 库存标识，缺货保留完整剩余数量。原 SO、HH、退回验收、原需求和已截停 XS 均不重建，旧轮次不可重新下发。页面按轮显示，累计实际出库仍以所有轮次事实汇总。执行前重查退款快照、平台申请及回传队列；无独立平台申请的协商单须人工核对平台/线下退款凭证，本期不自动退款。


## 平台来源与业务转单

平台列表 `/oms-order/platformExchanges` 独立展示平台申请、来源校验、版本、原单关联及转单结果。同步先保存 `oms_platform_exchange` 和不可变 `oms_platform_exchange_snapshot`；失效数量、缺失子单号和同版本冲突保留来源供核对。HH 表只承担业务方案与执行，同时保留执行所需的平台资料投影，使用 `platform_exchange_id` 关联来源。新方案不批量回填已有单据。

自动同步和自动转业务换货分别配置。自动转单每家公司每轮最多20条，按本地原订单与原平台子单唯一关联，无法关联时记录失败原因、至少间隔60秒重新核对；SKU描述不自动猜为OMS SKU，审核仍由业务换货负责。手工重试转单沿用同一HH，不新建SO。平台申请已结束且没有HH时标记无需转单；已关联业务后关闭或变更会保留原审核与库存事实，并交给现有业务核对流程。

同子单已有客服协商单时阻止自动重复建单，支持在平台详情核对数量、规格与实际来源后人工关联；关联直接复用原协商单并留业务事件，原协商履约不因此重复执行。协商单关联后的平台写操作仍需人工核对。

平台申请涉及尚未发出的销售商品时，在转单前即写入订单 `exchange_block_reason` 和 `PLATFORM_EXCHANGE` 域的问题标签。普通解除挂起和库存问题刷新不会绕过该阻断；已出库事实不回滚，现有仓库回传继续记账。平台资料关闭、实际发货或对应协商履约状态变化后重新核对来源阻断，不清除其他域的问题。

平台列表只做本地索引查询和分页，详情默认不返回原文和收件信息。来源原文使用独立 `order:exchange:raw` 权限，差异中的个人收件信息隐藏。转单和关联沿用业务审核权限，平台更新沿用同步权限；平台同意、拒绝、出入库和物流通知仍在业务换货执行。

部署先安装既有换货及统一接入表，再运行 `docker/local/configure_platform_exchanges.py`，更新 order 和前端。`configure_order_intake.install` 也会安装来源表及配置字段。回归为 `docker/local/test_order_intake.py` 与前端 `node tests/order-intake.cjs`；浏览器验收为 `docker/local/verify_platform_exchanges.py`，仅使用独立测试店铺、商品和可信模拟授权，证据在 `outputs/platform-exchanges`。

同公司扫描执行期间再次收到同步或配置唤醒，会在当前扫描结束后追加一轮，继续使用原有有界执行器。没有新增定时器或 MQ；数据库来源、转单状态与重试时间仍是可恢复依据。
