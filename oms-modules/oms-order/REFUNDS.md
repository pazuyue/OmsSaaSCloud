# 退款接入与两层转单

支持 JDP 同步、平台原文与版本留存、平台退款转 OMS 退款、人工方案审核、履约阻断及退款退回执行。页面资金成功只认平台 `SUCCESS`；审核不会支付退款，也不会代替库存记账。

## 入口和数据

平台来源位于「平台单据 → 平台退款」，执行位于「业务退款」，配置与补拉位于「订单与售后接入」。原业务订单详情的「退款记录」关联两个层次。保持一个原 SO，生成独立 TK 业务退款单，不新增销售订单。

| 数据 | 表 | 作用 |
|---|---|---|
| 来源事实 | `oms_platform_refund` | 按公司、店铺、平台退款单号唯一；保存最新采用的原文及解析结果 |
| 收到的报文版本 | `oms_platform_refund_snapshot` | 原文按散列去重；旧版本、无效版本、同版本冲突也留痕 |
| OMS 方案 | `oms_refund` | 用途、货物动作、审核依据、已采用来源快照；资金和货物状态分离 |
| 业务处理记录 | `oms_refund_event` | 转单、审核、平台更新记录 |
| 店铺接入 | `oms_refund_config` | 独立自动游标、自动转单、扫描间隔与租约 |
| 同步任务和单号结果 | `oms_refund_sync` / `oms_refund_sync_item` | 固定时间范围、逐页提交、失败重试；指定 ID 明确区分未找到 |

已审核快照不会被平台覆盖。状态变化而申请内容未变时，保持审核方案并推进采用版本；金额、类型、数量、理由等内容变化则重审。成功资金事实不会被后续关闭状态抹去。退款单关联的原订单、子订单不可被新报文迁移。

## 同步方式与性能

- 只读 `jdp_tb_refund`，按可信接入配置的 `seller_nick` 过滤；不写推送库。
- 自动窗口从独立退款游标出发，重叠两分钟，延迟三秒；单任务最多一天。按 `(jdp_modified, refund_id 数值)` 游标读取，每页最多 50 条，12 秒查询超时。
- 人工补拉最多 90 天，开始包含、结束不包含；指定 1–50 个**平台退款单号**不受时间范围限制。二者都不回退自动游标。字符串传递长 ID，SQL 排序和比较保留数值精度。
- 配置、任务、版本和游标都带公司条件；后台使用显式租户路由和有界执行器，借用现有带版本连接池。
- 任务失败保留当前页，最多五次自动失败后标记失败；人工重试继续原游标。配置租约在提交页前校验，失效不能提交。
- 建议源库管理员确认存在 `(seller_nick, jdp_modified, refund_id)` 索引；应用不会擅自对只读源库建索引。
- `ruoyi-job` 入口 `refundTask.scanAll()`，页面显示「天猫退款推送库同步与转单扫描」。默认新店铺自动同步、自动转单均关闭。
- 统一平台交互日志的「退款处理」展示 `JDP.refund.read`，记录类型「数据同步」、环境「本地操作」，不伪造 HTTP 或真实平台调用。可按平台退款号、TK、REFSYNC 任务号查询。

## 履约控制

收到未处理退款即物化 `refund_block_reason`，不依赖转单成功。审核、分仓、下发以及换出发货均受该阻断控制；人工恢复普通挂起不能跳过。退款先于订单到达时，在原订单拉取和生成 SO 后补充投影。

用途（退差价、补偿、运费、取消、其他、专项）与货物动作（继续履约、取消商品、在途拦截、拒收、协商退回）独立审核。继续履约须明确审核；取消商品必须选择实际商品明细与数量，不能由退款金额或平台 `num` 推算。拒收、拦截、退回方案必须存在实际出库事实。详情同时列出原子单各轮实际商品与发货明细，保留 A→B→A 的来源。

处理确切退款信号后，只解除该退款阻断；订单更新的商品、金额、地址、平台挂起等独立问题仍须处理。原订单报文缺少退款 ID 等可核对依据时保持阻断，避免错误放行。

## 货物执行

TK 下按实际发货明细建立 `oms_refund_return_plan`，明确商品、应退数量、接收仓、地址、运单和凭证。一个来源保持一份安排，停止后在原安排下生成新的仓库退回单；金额和平台 `num` 不决定退回数量。退款与换货在锁定原商品明细后共同校验原发货额度，保留各轮 A→B→A 的独立发货来源。

供链 `wms_refund_return`、`_event`、`_line`、`_review` 与换货退回共用 `WarehouseReturnService`，分别使用独立表、THK/THX 单号及库存幂等键。退款退回使用奇门 THRK，验签后按单据、连接、货主、仓库核对实收；原出库成本来自库存来源台账。接收货主须与原发货一致，良品与次品分别入账。入库表头、商品行、批次实收及日志中心均支持「退款退回入库」，可按 TK、THK、SO 和平台单号精确查找。

创建安排与仓库受理不增加库存。有效实收先持久化，再幂等入库；失败保留原消息与稳定记账键。重复回传不重复入库。退款回传的错货、超量、最终短收及截单后到货进入人工核对；拒绝不会增加库存，接受仍校验原来源额度、实际 SKU 和单据数量。接受迟到实收前须先截停其他安排。

退回单支持本地停止、仓库截单、明确失败重试、结果不明查询和剩余重新安排。已实收及入账保留，截单时的未收数量作为历史快照，不覆盖累计实收；新安排生成独立单据，需明确下发。物流登记只记录运输事实，物流签收不作为仓库实收。所有操作带计划版本和执行租约，不能在未知受理结果下覆盖原单。

货物状态为待退回、部分实收、待人工核对、待验收结案、已处理。验收结案前再次查询仓库；应退数量须由已入账实收与有凭证的不追回数量完整覆盖，无未结束安排、未记账实收或待核对回传。单独「无需追回」需差异权限、理由、凭证，不能伪造收货，也不能放行尚未明确处理的未发商品。货物处理完成且资金成功时 TK 才完成；结案后出现新待核对回传，会恢复货物核对及退款阻断，资金成功事实保留。

仓库回传保存 `progress_revision/notify_pending`；既有 `refundTask.scanAll()` 有界读取待同步进度并核对 TK，确认版本后才消除待办，避免新回传被旧确认覆盖。未完成入账不确认进度，后续继续重试；不依赖页面打开，不新增队列或定时器。手工刷新可立即核对。

未发取消沿用审核明确的商品和数量，先固定 `CFTK` 库存调整请求；结果不明继续使用原请求。仍有发货安排时，先到原订单撤回并确认仓库截停，再执行指定数量的取消；不会自动取消整单或其他商品。

## 边界

尚未启用平台审核/同意/拒绝退款写接口、验证码付款和快递公司拦截接口。平台资金操作仍在平台完成后同步；在途拦截登记及仓库退回截单不等于已拦截运输。仅退款和退货退款均可转 TK；平台申请类型来自来源版本，不由 OMS 擅自修改。

JDP 对交易完成后的部分售后、专项退款存在覆盖限制。指定退款号查不到仅表示本店铺推送库未找到，不能据此认为平台无申请。未覆盖或无法匹配的申请保留来源与失败原因，不据此认为平台无申请。

### 退回计划与逐次安排的展示和核对

- 一个来源退回计划包含多次 THK 安排，按计划数量汇总；各单的截停数量是历史快照，不与新单数量累加。
- 待核对回传单独列出条数和数量，不计入已确认实收、入账或新的退回需求。
- 单据截单仅作用于所选 THK；计划上的“截停全部未完成安排”逐单申请停止，以仓库确认结果为准，不处理回传、不撤销原入账、不表示永久放弃追回。
- 旧单待核对时允许先停止新安排，解决互相等待；有待核对回传时禁止继续下发和重新安排。确认迟到实收前，所有其他安排必须结束；确认后按实际剩余量生成下一次安排。拒绝只阻止本消息入账，必须留存实物核实和处置依据。
- “确认货物处理完成”明确展示计划数量、已入账、不再追回及阻断项。此操作只确认货物事项闭合，不执行收货、库存或退款；资金已成功时 TK 整体完成，否则继续等待资金。
- 仓库日志的 `result_summary` 记录当次交互结果，后续单据状态独立实时展示。未记录摘要的旧日志显示通用说明，不从当前状态反推当次数量，不回填历史业务。


### 多退款合包：一包一张有效THK

- TK退款单独立保存平台申请、审核、资金和货物结案。符合条件的多个来源安排关联同一RPK；RPK统一生成一张THK下发仓库。
- 固定校验同公司、同店铺、承运商和完整运单、接收仓/货主/连接、退回地址与联系信息。自动合包限同原平台订单；跨订单仅在配置允许、人工核实同一买家并留凭证时处理。
- `wms_refund_parcel_document`保存共同THK、下发快照、仓库受理号、交互租约、代次及截单结果；`wms_refund_parcel_member`保存明细行号和各TK原发货来源。
- `wms_refund_return`作为独立来源记账记录保留数量、虚拟仓和成本；包裹来源使用内部RSL标识，不下发仓库、不生成独立入库单。真正的THK只在共同单据表和出入库单据中生成一次，商品行保留来源。
- 店铺配置独立于JDP：人工关联、合包范围、数量上限、自动关联、可信物流、退回仓清单、自动下发和`collect_seconds`（默认120秒，0至3600秒）。新增来源后重新等待归集窗口；窗口结束统一下发，人工可确认全部范围后立即下发。
- 下发前可停止单张TK退回安排并移出预报范围。共同THK一旦生成，范围冻结。本期仓库适配未实现改单；不支持通过另建独立THK模拟追加，也不保留实收后补建独立THK流程。已有实收或冻结后新增来源显示结构化问题，指引更正真实物流、等待寄回或仓库差异核对。
- 仓库必须通过`taobao.qimen.returnorder.confirm`回传共同THK。RPK不能作为仓库单号，回传会拒绝并记录交互日志。仓库回传按连接、THK、受理号、仓库及货主验签校验，使用不可变消息快照去重。
- `orderLineNo`采用共同单据来源明细行号。行号明确或SKU只有一个有效来源时自动分配；单SKU同品相全部收齐可按各自剩余量分配；同SKU部分实收存在多个来源、混合品相、超收、最终短收、截单后实收保留待核对。缺失或错误行号不猜测。
- 归属核对必须保持原消息每行、良次品数量守恒，来源须在该THK原下发快照内且不超过剩余额度。原成本、原虚拟仓幂等入账，资金不自动变更。拒绝入账必须留依据和实物处置凭证。
- 共同THK整单截停须确认当前包裹版本及全部关联退款影响。单张TK不能静默取消其他TK；已实收入账保留。确认截停且无未核对消息后，可为未实收来源重排下一代共同THK。旧单迟到实收需先截停后续共同THK，再人工核对，防止重复收货。
- UI以包裹展示共同THK、退款来源、计划/仓库报告/已分配/入账/待核对数量，并提供统一下发、原单查询、重试、整单截停和剩余重排。仓库日志支持按任一TK、共同THK、SO或平台单号查到同一交互，不复制日志。出入库单表头与批次明细采用共同THK，库存按来源记录。

验收：`python docker/local/verify_refund_shared_thk.py`，新建独立TEST订单与3张TK（2+1+1件），统一下发一张THK，模拟签名回传3件同SKU部分实收，保留待归属核对且库存未增加的单据供验收。输出`outputs/refund-shared-thk/`。单元回归覆盖按行实收、全部收齐、唯一剩余来源、部分歧义、消息冲突、重复、截单迟到及剩余重排。

仅新增结构，不迁移历史业务数据；不对接真实平台付款。

### TK详情与退回包裹的独立展示

- TK详情以当前退款为范围，展示平台、审核、资金、商品来源、计划退回、已确认实收和入账。原订单商品与发货来源折叠展示；共享THK的仓库操作不在单TK计划上重复提供。
- 未分配回传存在时，当前TK显示“待确定（已确认0件）”或“已确认X件，另有待分配”，不把整个包裹回传数量计作本TK实收。包裹关联摘要同时明确本TK数量和整个包裹数量。
- 独立包裹抽屉集中展示共同THK、物流、全部TK来源、逐次回传及分配记录、入账和共同截单。列表“查看退回包裹”和详情中的包裹摘要均进入同一抽屉，优先打开有待分配回传的包裹。
- 待分配卡说明原回传数量、SKU与明细行缺失等阻断原因。仓库未结束收货时显示“尚未回传”，不提前认定少收。分配表按原THK/明细行限定来源，逐行校验良次品守恒及来源剩余额度；后端继续作为最终校验。
- 回归：`node tests/refund-parcel-presentation.cjs`；只读页面验收 `python docker/local/verify_refund_parcel_separation_ui.py`，使用保留的三TK共同THK测试单，不提交实收分配或共同截单。

### 独立退货规则入口

- 导航为“订单 → 售后规则 → 退货规则”，路径 `/oms-order/afterSaleRules/returns`，按店铺保存。退款列表、退款详情和关联包裹内的快捷入口均定位该页面；详情入口带当前店铺及返回退款单的链接。
- 订单与售后接入页面不再承载合包设置。独立页面只读取规则所需的公司店铺清单和所选店铺规则，不读取JDP接入配置，不逐店请求全部规则。
- 店铺清单使用 `GET /refunds/parcel-configs/catalog`，与规则读写一致使用 `order:refund:config`，公司取登录身份。现有策略、配置版本和仓库能力校验保留，未增加自动分配策略。
- `python3 docker/local/configure_after_sale_rules.py` 安装独立菜单，沿用现有退款配置权限；`configure_refund_goods.py` 的权限安装会一并安装此菜单。只调整导航，不迁移业务单据或修改店铺规则值。
- 前端规则编辑器改为页面内编辑，保存后重新读取配置版本，支持继续保存；店铺切换时丢弃旧响应，指定店铺不可见时不回退至其他店铺。
- 验证：`node tests/refund-return-rules.cjs`、`OrderIntakePermissionTest`；本地只读页面验收 `python docker/local/verify_return_rules_ui.py`。

### 退货规则店铺列表与编辑抽屉

- 首页每家天猫店铺一行，展示实际生效的默认或保存配置、自动合包/下发开关、自动处理仓、归集等待、固定实收分配规则、版本和更新时间。默认规则生效不等于功能关闭；停用店铺仍展示，但仅允许查看。
- `GET /refunds/parcel-configs` 使用 `order:refund:config`，登录公司决定范围。支持店铺名称/渠道ID、自动合包、自动下发、DEFAULT/CUSTOM配置情况筛选和服务端分页（每页最多50）。概览按店铺搜索范围统计，不随配置开关筛选改变计数口径。
- 每次列表请求读取一次公司店铺目录和一批公司配置，合并后筛选分页；只为当前页按需批量读取仓库名称。列表不逐店查询配置、不加载各店铺仓库能力。仓库名称不可用时返回编码和提示，不改写规则。
- 查看抽屉禁用表单且不显示保存按钮；编辑抽屉保留原版本校验，保存后刷新列表及最新版本。停用店铺规则允许读取，写入仍由后端店铺状态校验拒绝。
- 退款详情的channelId上下文定位列表并自动打开该店铺抽屉，关闭后保留定位行；无效店铺不回退打开其他店铺。列表按钮不自动保存任何开关。
- 验证：`RefundParcelPolicyTest`覆盖默认值、分页筛选、公司隔离、停用店铺、仓库调用次数及失败降级；`node tests/refund-return-rules.cjs` 和 `python docker/local/verify_return_rules_ui.py` 覆盖列表及抽屉只读验收。

### 退款接入消息队列

- `REFUND_PULL` 每次消费一页，读取 `jdp_tb_refund` 并保存平台退款；来源快照、退款更新阻断、转单通知及任务分页游标在同一事务提交。指定退款单号补拉独立留痕，不改变自动游标。失败自动窗口阻断后续自动窗口越过游标。
- `REFUND_CONVERT` 独立转业务TK，沿用公司、店铺、平台退款单号的身份及原子单校验；同一个TID允许多个独立申请。平台版本更新使旧通知失效；重复消费不重复建TK。转单不自动同意退款、执行资金、截单或操作库存。
- 退款先到时消息等待原业务订单，不消耗失败预算；原订单到达后继续关联。来源异常及原子单不匹配明确失败；原问题修复后从原平台退款或消息任务重试，保留父消息链。平台关闭申请可结束待转单任务；已有TK继续沿用原关闭及货物核对规则。
- 手工转单接口返回已提交后台处理；即使店铺关闭自动转单，显式申请仍使用相同队列。自动扫描仅发现任务并落通知，不再直接读取JDP或转单。货物后续处理及包裹自动化仍沿用现有流程。
- 消息队列管理可分别配置、暂停拉取与转单；现有同步任务、平台退款列表和详情批量显示最新消息进度及链路。公司停用后不进入新的退款接入处理。默认每种队列1个消费者、预取1，订单服务总并发上限仍为12。
- 安装：`configure_messaging.py` 添加任务 `work_version`、平台退款 `intake_version/conversion_requested` 与两条队列策略；不回放历史单据。回归：`test_stock_sync.py --refund-messaging`、`ruoyi-ui/tests/refund-messaging.cjs`；真实本地验收：`verify_refund_messaging.py`。
