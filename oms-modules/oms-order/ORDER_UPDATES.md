# 订单更新（本期）

平台订单最新事实与已采用的履约快照分开保存。接收来源更新不会覆盖业务商品、购买数量、原金额、需求或库存台账。

## 分类与边界

- 规格描述无法确定只是展示修正时，保守按商品变更阻断。
- 展示信息、正常平台发货/完成状态同步；平台发货状态与实际出库不符时提示核对。
- 收货信息变更由人工确认。原未发履约先通过 REPLAN 撤回；仓库结果、库存回执未确认时不能应用。应用后重新审核和按新地址分仓、匹配快递，原发货单地址保持不变。
- 商品、规格标识、数量、金额及退款信号先识别、阻断、留痕。无强制采用按钮，后续售中、售后或纠错申请引用更新记录处理。
- 退款成功保留待处理信号，后续报文省略退款字段不代表已处理。退款申请撤销可以解除该平台信号，但原审核失效，其他阻断和人工挂起不解除。
- 本期明细识别、整单阻断新增履约；不自动通知仓库截单。真实出库回传、查询及记账继续处理。

## 持久化及并发

`oms_order_update` 保存有效版本、平台完整快照、字段差异、影响类别、处理状态及关联截单 ID。平台订单保存 `update_version/update_state/update_categories/update_summary` 当前投影，列表按索引查询，无逐行 JSON 解析或仓库调用。详情按公司和订单最多返回 30 条历史摘要，差异在展开时单独加载，原始报文不随更新接口返回。

较旧来源版本跳过；相同内容不会重复生成日志。相同来源时间出现不同关键内容保留冲突，不覆盖当前平台快照；可信的新来源版本重新确定差异。处理前校验更新版本；与拉单、挂起、下发、截单使用相同的店铺→平台→业务订单→发货单锁顺序。

收货信息采用只修改业务快照的收货字段，不能顺带采用同一报文的商品或金额变化。其他类别从采用后的快照重新核对。关键变更使原审核失效；已排队下发沿用实际执行时的审核和平台阻断校验。

## API / 权限

- `GET /orders/platform/{id}/updates`：`order:order:query`
- `POST /orders/platform/{id}/updates/recipient`：`order:order:update`，提交 `update_version/reason`
- `POST /orders/platform/{id}/updates/withdraw`：同时要求 `order:order:update` 和 `order:order:cutoff`，提交同上
- 业务列表 `updateState`：WAITING / PROCESSING / ERROR / COMPLETED

`docker/local/configure_order_updates.py` 安装表、当前投影和权限；并入业务订单标准安装。无历史回填，无新增队列或定时任务，不改变原任务开关。

## 验证

`OrderUpdateServiceTest` 覆盖库存不变、连续更新、来源冲突、过期版本、跨公司、收货信息局部采用、原挂起保留、未撤回发货阻断、退款撤销重审及索引筛选。

`docker/local/verify_order_updates.py` 创建独立本地只读推送库及新测试店铺、商品和订单，经正常指定 TID 补拉生成更新；浏览器执行撤回与收货信息采用，再重新审核分仓。保留商品/数量与退款同时变化的待处理订单。没有真实平台通知或仓库下发。
